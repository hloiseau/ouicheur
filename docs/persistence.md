# Shared persistence

Version 1.3.2 introduces a small asynchronous catalog contract shared by SQLite and PostgreSQL. The existing application still uses SQLite by default. No database server or configuration change is required for existing installations.

Version 1.3.3 extends the implemented slice to owner creation, reading and editing of full gift metadata, variants and alternative offers, alongside list metadata and purchase status. Shared gift validation and decisions live in `lib/gift-persistence.ts`; `SqliteGiftStore` and `PostgresGiftStore` implement the same owner service. The existing SQLite import/copy paths retain synchronous compatibility using those decisions. Gift reads return metadata, not reservation or financial totals. Validation, surprise-disclosure rules, share revocation decisions and audit decisions live in `lib/catalog.ts`. The existing HTTP endpoints use `catalogService` with `SqliteCatalogStore`; synchronous internal callers keep compatibility facades using the same rules. SQLite transactions contain no `await`.

`PostgresCatalogStore` accepts a pool compatible with node-postgres and a **server-verified tenant UUID**. It uses transaction-local tenant context, a single connection per transaction, row locks and an audit record committed atomically with each mutation. Table policies enforce tenant scope; the runtime role must not own the tables, be a superuser or have `BYPASSRLS`. Application permissions remain necessary inside each tenant. The `Access` object is trusted server context, never a request payload. RLS is not authentication or protection against a compromised application with DB credentials.

The driver is injected; `pg` is only a development dependency of this repository. Integrators supply their own bounded pool and verified TLS settings. Separate migration credentials from runtime credentials. Pending catalog migrations require a dedicated schema-owner role with `BYPASSRLS` (or a test superuser), so backfills see every tenant despite forced RLS. Never provide those credentials to the runtime. `migrateCatalog` applies the ordered checksum-verified migrations under a transaction-scoped advisory lock. `provisionCatalogTenant` and `grantCatalogRuntime` are administrative operations, not runtime HTTP endpoints. Role creation and secret management belong to the deployment operator.

Version 1.4.1 adds the `participationService`, shared decisions in `lib/participation.ts`, and SQLite/PostgreSQL adapters for reservation tokens, quantity, contribution intents/declarations/pledges, owner review, manual confirmations, revisioned corrections and funding totals. All mutation decisions run inside the adapter transaction. Existing SQLite routes use this service; synchronous internal callers share the same decisions. No SQLite schema change is required.

The PostgreSQL schema remains partial: lists, gift metadata/offers, participation, the financial ledger, per-tenant reveal state and audit. Categories and priorities are tenant-scoped references. It **does not implement login, the complete HTTP/public rendering layer, uploads, notification delivery, workers or data migration from SQLite**. Do not point the existing application at PostgreSQL or infer whole-application support from these contracts.

Migration `003-participation.sql` adds per-tenant payment settings, tenant-scoped payments and append-only payment events, and an append-only participation outbox. Runtime can insert/update reservations, contributions and payments, but cannot delete them, alter payment events or alter tenant settings. `configureParticipation` is an operator-only administrative operation; it validates the existing PayPal.Me name and strict-declaration option. It cannot change gift or household currency. Captured PayPal recipients remain unchanged for existing intentions.

Amounts are integer cents. Promises remain separate from received funding and never expire automatically; cancelling a promise prevents its later declaration. Normal mode counts declarations immediately; strict mode requires owner approval. Confirmed payments replace declarations, including after refunds. Unknown fees remain explicit. Actual confirmed payments may arrive late or exceed the original target: recording received money must not silently discard it. Corrections require the current revision and an event ID; repeated identical events have one effect. No external transfer or provider verification is performed. Caller-supplied provenance cannot mark a manual entry as verified.

Reservation tokens are stored hashed; contribution IDs preserve the existing 256-bit bearer-link contract and must be treated as secrets. Token status responses exclude current private gift metadata, donor messages and transaction references. Funding totals and financial administration require owner context and surprise disclosure. PostgreSQL outbox events contain only the event kind, list ID and entity key (SHA-256 of the bearer contribution ID for declarations; the non-secret reservation ID for reservations). The outbox has no recipient address or delivery implementation. A future consumer must resolve these keys and re-check account rights, current preferences and surprise protection before creating addressed notifications; no delivery or deduplication guarantee for external email is claimed.

Migration `002-gift-details.sql` upgrades the released `001` schema without rewriting it. Existing purchase-only gift rows keep their IDs, list and purchased state; `details_ready=0` prevents presenting invented metadata. An explicit owner update supplies the missing details and keeps the purchase state unless changed deliberately. No historical creation timestamp or missing metadata can be recovered from `001`.

Gift metadata and purchase mutations share a transaction-scoped advisory lock per tenant, protecting duplicate detection, offer ownership and list positions. Different tenants are independent; this is not a capacity guarantee. Metadata reads hold gift/list row locks through the offer read for a consistent result and surprise policy. Participation mutations and token reads that expire state acquire the same tenant advisory lock before checking quantities, funding, contribution history or ledger events. This deliberately serializes participation within one household; lock/statement timeouts bound waits. A future narrower locking strategy requires concurrency tests and measurements. Metadata updates preserve stored currency, source identity, creation timestamp and extracted prices unless a new extraction is supplied. Active reservations prevent reducing quantities; any contribution history prevents removing a budget.

## Verification

`npm test` runs the existing regression suite and the catalog contract on SQLite. `npm run test:postgres` runs the same contract plus PostgreSQL isolation/concurrency tests against a real server. It requires `POSTGRES_TEST_URL` pointing to an empty disposable database named `ouicheur_test_*`, with permission to create test roles and the schema. Test users and data are synthetic; use a disposable server, as the test-created schema and roles are retained until that server is removed. The test suite refuses an existing `ouicheur` schema and never silently skips when PostgreSQL is absent.

CI provisions PostgreSQL 18 separately from the application images. The suite checks shared business behavior, rollback after audit failure, default-deny RLS, cross-tenant writes and composite foreign keys, pooled-connection context after commit/error, owner-role rejection, concurrent migrations, migration checksums, and idempotent purchase changes from two independent pools, concurrent duplicate detection, metadata/purchase interleaving, offer ownership and additive schema upgrades. Participation contracts also exercise access/surprises, immutable reservation snapshots, offline modes, expiry, refunds, ledger idempotence, outbox rollback and tenant-scoped bearer links. Concurrent tests cover the final quantity, remaining budget, reservation-versus-intent, repeated declaration/confirmation and conflicting revisions. Two pools are not proof of a complete multi-replica web application or of capacity under load.

The PostgreSQL SQL is not a migration for the application's SQLite schema. Do not execute it using the existing SQLite management commands.
