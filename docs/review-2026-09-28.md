# Ouicheur : audit de partage et feuille de route

État étudié le **28 septembre 2026** : dépôt public
[`hloiseau/ouicheur`](https://github.com/hloiseau/ouicheur), commit
[`285b41e`](https://github.com/hloiseau/ouicheur/commit/285b41eca5adb181a9a340dea10a636d12865969).
Cette revue porte sur le code, la documentation, l'historique accessible, la CI
et les métadonnées de l'image. Aucune instance personnelle ni donnée réelle
n'a été consultée. Les évolutions proposées ci-dessous ne sont pas implémentées.

## Avis

**Oui, le code est open source sous MIT. Oui, il est partageable pour des premiers
utilisateurs avertis. La publication dans les catalogues NAS demande encore une
version identifiée et des essais sur les plateformes.** Le dépôt public, la
licence MIT complète et la possibilité de construire depuis les sources sont
présents. `private: true` dans `package.json` empêche une publication npm
accidentelle ; ce champ ne rend pas le code propriétaire.

Le socle est déjà conséquent : setup protégé par code, compte propriétaire,
sessions hachées, mots de passe scrypt, contrôle d'origine, quotas, filtrage des
destinations réseau, images locales réencodées, sauvegarde/restauration SQLite,
interface EN/FR, imports Amazon/Throne/CSV/JSON, quantités, doublons explicites,
modération et registre des contributions. Il n'est pas nécessaire de recréer
ces fonctionnalités pour lancer une première diffusion.

### Contrôles exécutés pendant cette revue

- `npm ci --no-fund` : réussi avec le lockfile du dépôt.
- `npm test` : **49 tests réussis**, aucun échec ni test ignoré.
- `npm run format:check` : réussi sur la version étudiée.
- `npm audit --json` : **0 vulnérabilité connue signalée** à cette date. Le
  résultat concerne npm, pas Chromium, Debian ou toute vulnérabilité inconnue.
- Recherche ciblée de clés privées, tokens GitHub et identifiants AWS dans
  **221 blobs uniques des 10 commits accessibles** : seul le certificat de test
  possède sa clé privée de fixture. Pas de secret réel trouvé par ces motifs ;
  ce contrôle n'est pas un scan exhaustif de toutes les formes de secret.
- Rendu du candidat TrueNAS avec la bibliothèque amont 2.3.14 : deux scénarios
  passent, ixVolumes sous `1000:1000` et chemins hôte sous `568:568`. Montages,
  port interne, utilisateur et restrictions vérifiés dans le résultat.
- XML Unraid : syntaxe, profil et paramètres de déploiement vérifiés localement ;
  **Validate/Scan** officiel demande la connexion Unraid et un dépôt prêt.

Les nouveaux résultats de CI de la proposition sont à lire sur sa pull request.
`npm run check` et `npm run build` ne peuvent pas être validés dans cet
environnement : le compilateur TypeScript échoue sur `/proc/self/exe` absent et
Next.js sur `uv_resident_set_memory` indisponible. Ce sont des limites de ce
runtime, pas des erreurs applicatives démontrées. Aucun Docker local, TrueNAS
ou Unraid n'est disponible ici ; aucun nouveau succès E2E/NAS n'est revendiqué.

## Points à traiter avant une diffusion large

1. **Livraison identifiable et retour arrière** : version numérotée, changelog,
   image correspondante, sauvegarde avant migration et restauration documentée.
   Une simple bascule vers une vieille image n'annule pas une migration SQL.
2. **Test de la vraie installation** : création des volumes, permissions,
   initialisation, import Chromium, redémarrage, mise à jour et restauration sur
   chaque NAS. Le test HTTP de santé ne valide ni les imports ni les sauvegardes.
3. **Contributions déclaratives** : `fundingTotalsSql` dans `lib/gifts.ts`
   additionne les déclarations ; `createIntent` dans `lib/payments.ts` ferme les
   nouvelles contributions à l'objectif. C'est le comportement voulu et décrit
   dans le README. Un visiteur peut donc déclarer un versement inexistant et
   saturer provisoirement un objectif jusqu'au refus par le propriétaire.
   Proposer un mode de validation stricte facultatif et distinguer les montants
   déclarés et validés améliorerait l'usage public. Ne pas changer silencieusement
   le comportement des installations existantes.
4. **Données privées et signalement** : les sauvegardes contiennent le hachage du
   propriétaire et les messages privés. Ne pas les utiliser comme pièces jointes
   publiques de support. Compléter le canal de signalement privé et un export de
   diagnostic expurgé. Les protections existantes sont utiles, sans constituer
   un audit de sécurité exhaustif.
5. **Redistribution des binaires** : la licence MIT du projet n'annule pas les
   obligations des dépendances. Vérifier notices, attributions et accès au code
   source applicable dans l'image finale, notamment les composants natifs.

## Fonctionnalités à prioriser

Effort relatif : petit = évolution circonscrite ; moyen = plusieurs parcours et
tests ; grand = changement de modèle de données ou d'architecture. Ce ne sont
pas des engagements de délai.

| Priorité | Fonctionnalité                                       | Valeur et critère de réussite                                                                                                                        | Effort |
| -------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| P1       | Listes non répertoriées ou privées, liens révocables | Partager avec famille/amis sans indexation ; pages, images et API respectent la visibilité ; un lien révoqué ne donne plus accès                     | Grand  |
| P1       | Réserver « je l'offre » sans PayPal                  | Éviter les doubles achats ; réservation anonyme avec lien de gestion, expiration et quantité réservée ; ne jamais créer un faux paiement             | Moyen  |
| P1       | Mode strict facultatif pour contributions            | Fermer l'objectif seulement après validation si activé ; afficher séparément déclaré/validé ; préserver les règles existantes par défaut             | Moyen  |
| P1       | Sauvegarde depuis l'administration                   | Déclenchement et téléchargement protégés, historique et état ; puis planification/rétention ; restauration éprouvée, pas un simple export JSON       | Moyen  |
| P1       | Notifications facultatives                           | Informer d'une déclaration, d'une réservation ou d'un échec d'import ; commencer par SMTP ou ntfy auto-hébergé, sans message privé envoyé par défaut | Moyen  |
| P1       | Plusieurs listes et événements pour un propriétaire  | Anniversaire, Noël, projet personnel ; partage et archivage par liste ; conserver les catégories existantes                                          | Grand  |
| P2       | Ajout mobile rapide et partage                       | Lien direct/QR par liste, aperçu social respectant la confidentialité, puis cible de partage PWA authentifiée ; mesurer d'abord le besoin            | Moyen  |
| P2       | Actualisation manuelle prix/disponibilité            | Signaler une variation datée, demander confirmation avant de changer l'objectif ; garder le repli manuel quand le marchand refuse                    | Moyen  |
| P2       | Tableau de santé et diagnostic expurgé               | Version, état du stockage, espace disponible, état Chromium et dernière sauvegarde ; téléchargement sans secrets ni données de paiement              | Moyen  |
| P2       | Nettoyage et croissance des données                  | Pagination admin, purge des imports/intents obsolètes avec conservation du registre utile, détection d'images orphelines et limites disque           | Moyen  |
| P2       | Image ARM64 testée et empreinte réduite              | Construire et tester SQLite, Sharp et Chromium sur ARM64 ; mesurer avant de promettre la compatibilité ou une image légère                           | Grand  |

Je commencerais par la distribution fiable, puis **confidentialité + réservation
sans paiement**, qui rendent Ouicheur utile à davantage de foyers tout en
conservant son modèle simple. Les comptes familiaux multiples, SSO/OIDC et
paiements automatiques viennent après validation de la demande : ils changent
fortement le produit. Ne pas promettre une confirmation automatique PayPal.Me
sur compte particulier ; l'étude des paiements du dépôt expose déjà cette limite.

Le README anglais, des captures avec données fictives, une page de démarrage
courte et un changelog sont des améliorations de diffusion prioritaires même
s'ils ne sont pas des fonctionnalités métier.

## Proposition aux catalogues

| Plateforme | Livrable préparé                                                                                                | Ce qui reste avant disponibilité                                                                      |
| ---------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| TrueNAS    | `deploy/truenas/ouicheur/` avec métadonnées, questions, modèle Jinja et deux jeux de test ; demande d'app prête | Proposition publique, génération/validation officielles, essais NAS et revue des mainteneurs          |
| Unraid     | `templates/ouicheur.xml`, `ca_profile.xml` et guide d'installation                                              | Fusion du modèle, image corrigée, essai NAS, connexion Unraid, Validate/Scan puis soumission et revue |

Les deux paquets utilisent une image réellement existante et épinglée par commit
pour l'évaluation. Ils doivent adopter la version corrigée avant diffusion
stable. « Proposition préparée », « soumise », « acceptée » et « installable
depuis le catalogue » sont quatre états différents. Consulter la pull request
et les liens de soumission pour le statut après cet audit.
